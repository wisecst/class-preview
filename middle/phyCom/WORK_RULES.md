# 피지컬 컴퓨팅 수업자료 개발 규칙

## 0. 작업 시작 최우선 규칙

사용자가 이 저장소와 관련된 작업을 지시하면, Work의 첫 번째 작업은 반드시 GitHub 접근이어야 한다.

로컬 파일 확인, 현재 상태 확인, 코드 분석, 저장소 조사, 브랜치 확인, WORK_RULES.md 읽기 등 어떤 작업도 GitHub 접근보다 먼저 수행하지 않는다.

작업 시작 순서는 반드시 다음과 같다.

1. 사용자 명령 수신
2. 즉시 GitHub에 접근
3. 최신 원격 main을 기준으로 작업 브랜치를 생성하거나 사용할 작업 브랜치를 준비한다.
4. 실제 파일 수정 전에 현재 브랜치가 작업 브랜치인지, 기준 HEAD와 기존 변경 사항이 무엇인지 확인한다. main에서 실제 수정을 시작하지 않는다.
5. 읽기 전용 확인이나 로컬 수정·검증을 위해 원격 임시 write 또는 빈 줄 추가·복구를 하지 않는다. 필요한 권한은 해당 작업에서 확인한다.
6. 사용자가 금지한 commit·push·branch/ref 변경·배포는 수행하지 않는다.
7. 그 다음 WORK_RULES.md 전체 확인
8. 현재 브랜치/HEAD 및 작업에 필요한 상태 확인
9. 사용자 요청 작업 수행
10. 필요한 범위만 검증
11. 요청된 커밋/푸시/배포 수행

핵심 순서는 항상

사용자 명령
→ 즉시 GitHub 접근
→ 작업 브랜치 생성
→ 작업 브랜치·기존 변경 확인
→ 점검
→ 실제 작업
→ 직접 영향 범위 검증
→ 요청된 커밋/푸시/배포

이다.

GitHub 접근 전에 로컬 저장소 조사, 코드 분석, 파일 검색, 브랜치 확인, 상태 점검을 먼저 수행하지 않는다.

이 규칙은 이 저장소에서 수행하는 모든 개발 작업보다 우선한다. 사용자가 명시적으로 이 절차를 생략하라고 지시한 경우에만 생략한다.

이 문서는 `wisecst/class`의 `middle/phyCom/` 작업에 적용한다. 작업의 기준은 최신 원격 Git 상태, 이 문서, `WORK_STATUS.md`, 실제 코드다.

## 1. 작업 범위와 보안

- 사용자의 구체적인 수정 지시를 우선한다. 지정한 범위를 임의로 넓히거나 범용 시스템으로 재설계하지 않는다.
- 작업 범위는 `middle/phyCom/`이다. `wisecst/physical-tools/circuit-editor/`는 읽기 전용 참고자료이며 수정하지 않는다.
- 범위 밖 경로 접근·수정이나 보안 경계 변경이 필요하면 먼저 사용자 허가를 받는다.
- 공개 문서와 외부 공유에 개인정보, 학생정보, 계정·보안정보, 미공개 수업모형·연구·아이디어를 포함하지 않는다.

## 2. 작업 방식

기본 흐름은 **현재 상태 확인 → 직접 원인 확인 → 최소 수정 → 직접 영향 범위 검증**이다.

- 작업 시작 시 요청 기능과 관련된 `middle/phyCom/common/`의 기존 구현 존재 여부와 대상 페이지의 로딩·호출 관계를 먼저 확인한다. 저장소 전체나 정상 동작 중인 다른 페이지를 매번 다시 분석하지 않는다.
- 이전에 확인한 구조와 검증 결과는 관련 코드나 근거가 바뀌지 않은 한 재사용한다. 원인을 찾지 못할 때만 조사 범위를 넓히며, 무관한 문제는 현재 작업에 포함하지 않는다.
- 사용자가 지정한 기존 구현(예: 다른 페이지의 이동 방식, 팝업 동작)을 참고할 때도 아래 공통 구현 우선 원칙을 적용한다.
- 요청 해결에 필요한 기존 코드만 살펴 최소한으로 고친다. 중복 구현이나 임시 override를 추가하지 않으며, 관련 없는 정리·리팩터링·기능 추가는 하지 않는다.
- 공통 코드를 바꾸면 실제 영향이 예상되는 페이지를 확인한다. 큰 구조 변경이나 범위에 영향을 주는 선택이 꼭 필요하면 이유와 영향을 설명하고 진행 지시를 받는다.
- 특정 로컬 기기·폴더·프로그램에 의존하지 않도록 하고, 가능한 경우 GitHub를 기준으로 작업을 이어갈 수 있게 한다.

### 공통 구현 우선 원칙 (매 작업 기본 적용)

- 공통 구현이 존재하는 기능의 canonical source(수정·재사용의 기준 원본)는 `middle/phyCom/common/`이다. 사용자가 매번 공통 기능 적용을 지시하지 않아도 이 원칙을 적용한다.
- Entry engine, coding setup, hardware connect, navigation, stage, page numbers 등은 관련 common JS/CSS와 실제 호출 관계부터 확인한다. 공통 구현이 있으면 같은 기능을 개별 모듈에 새로 구현하지 않는다.
- 개별 모듈에서 기존 중복·병행 구현을 발견하면 그것을 기준으로 확장하지 않는다. common 호출 어댑터인지, 수업별 데이터·설정인지, 과거 복제 구현인지와 현재 로딩 여부를 먼저 확인한다. 파일명만으로 중복이나 삭제 대상을 판단하지 않는다.
- 공통 기능 변경이 필요하면 canonical common 구현을 최소 수정한다. 호출·로딩 관계로 직접 영향 모듈을 식별하고 그 범위만 검증한다. 수업별 데이터·설정은 기존 공통 API와 어댑터를 통해 연결한다.
- 공통 구현을 우회하는 새 CSS/JS, override, 복제 파일 또는 모듈 전용 공통엔진을 만들지 않는다. 기존 모듈별 스타일·어댑터도 공통 기능의 별도 기준 원본으로 삼지 않는다.
- 요청 범위 밖의 기존 중복 파일은 임의 삭제하거나 대규모 통합하지 않는다. 제거·통합 후보는 경로, 대응 common 기능, 로딩 상태를 기록하고 별도 작업 범위가 정해졌을 때 처리한다.

### 확인된 병행 구현과 후속 검토 대상

아래는 경로·호출 관계를 확인한 목록이며 즉시 삭제 목록이 아니다. 통합 시 모듈 고유 동작을 구분하고 직접 영향 범위를 다시 확인한다.

| 개별 경로 | 대응 canonical common 경로 | 확인된 관계 / 후속 검토 |
| --- | --- | --- |

| `servo-motor/entry-common.js` | `common/js/entry-engine/{grammar,tabs,renderer}.js` | 현재 로딩되는 공통 renderer 연결 어댑터. DOM→블록 변환 등 공통화 가능 부분만 검토하고 수업 진행·결과 연결은 보존. |

## 3. 수업 내용과 기술 정확성

- 교육과정·교과서는 수업 내용 판단이 필요한 작업에서만 관련 부분을 직접 확인한다. 기준 교과서는 첨부된 5개 분할 PDF 전체이며 `PDF1-1 → PDF1-2 → PDF2 → PDF3 → PDF4` 순서의 한 권으로 취급한다. 오브젝트·코드·변수·센서값·동작 흐름을 임의로 바꾸지 않는다.
- 내용·회로·코드·실행 결과의 기술적 판단에는 사용자가 지정한 자료, 프로젝트 내 근거, 모듈 공식 사양 또는 신뢰할 수 있는 기술자료를 필요한 범위만 확인한다. 기억이나 추측만으로 근거를 대체하지 않는다. 규칙 문서 정비 등 수업 내용 판단이 없는 작업에 교과서 전체 확인을 요구하지 않는다.
- 구현 뒤에는 변경한 설명·회로·코드·시각 표현이 실제 원리 및 결과와 일치하는지 확인한다. 검토 범위는 수정 내용에 맞춘다.
- 기술 오류, 오개념 위험 또는 근거 간 충돌을 발견하면 임의로 수업 설계를 바꾸지 말고 위치·근거·영향과 필요한 판단을 사용자에게 알린다. 표현 취향과 사실 오류를 구분한다.

## 4. 검증

- 수정 기능과 직접 영향 범위만 검증한다. 페이지 수정은 해당 페이지, 공통 변경은 실제 영향 페이지를 대상으로 한다. 정·역방향 전환, 팝업, 애니메이션, 전체화면, 반응형 등은 변경과 관련된 항목만 확인한다.
- 전체 페이지 검증은 공통 핵심 로직 변경, 여러 페이지에 걸친 큰 변경, 영향 범위를 특정할 수 없는 경우, 사용자의 명시적 요청 또는 전체 배포 검증이 필요한 경우에만 한다.
- 이미 통과한 검사는 관련 코드가 바뀌지 않았다면 반복하지 않는다. 검증에서 오류가 나오면 직접 원인을 해결하고 영향을 받는 검사를 다시 한다.
- 레이아웃·위치·크기·애니메이션 등 실제 화면 확인이 필요한 항목은 브라우저에서 확인한다. 수행하지 않은 브라우저 검증을 완료라고 쓰지 않고, 미검증 범위를 분명히 밝힌다. 브라우저 사용이 불가능해도 가능한 정적·기능 검증과 안전한 배포를 진행할 수 있다.

## 5. 커밋, main 및 Pages

모든 실제 수정은 작업 브랜치에서 수행한다. 기본 흐름은 다음과 같다.

**최신 원격 main 확인 → 작업 브랜치 준비 → 관련 common·대상 구현 확인 → 최소 수정 → 실제 변경 파일·diff 확인 → 직접 영향 범위 검증 → 요청된 작업 브랜치 commit·push → 결과 보고 및 대기**

- 검증 완료 후에도 사용자의 명시적 승인 전에는 main에 반영하지 않는다. 일반 수정 요청, 작업 브랜치 commit·push 또는 검증 성공은 main 병합·push 승인으로 간주하지 않는다.
- 사용자가 main 반영을 명시적으로 승인한 경우에만 최신 원격 main과 충돌·회귀 위험을 확인한 뒤 반영한다. 충돌, 검증 실패, 다른 작업을 덮어쓸 위험 또는 불명확한 범위가 있으면 반영하지 않고 보고한다.
- Preview는 승인된 main 반영 후 기존 자동 동기화만 사용한다. `class-preview`에 별도 수동 복제·push·배포 구현을 만들지 않는다. 배포 금지 지시가 있으면 준수한다.
- `class`가 유일한 개발 원본이다. 학생용 `2022-M-phycom`은 별도 지시 없이 수정하지 않으며, `version/phycom-v1.0`과 기존 보존 버전은 수정하지 않는다.
- 승인된 반영·배포는 한 요청의 변경을 가능한 한 모아서 처리한다. 배포 상태와 실제 확인한 화면 범위를 구분하고 배포 성공을 브라우저 검증 완료로 간주하지 않는다.

## 6. WORK_STATUS.md와 인수인계

- 새 작업은 이 문서와 `WORK_STATUS.md`를 확인하고, 최신 원격 브랜치·HEAD·작업 상태를 기준으로 이어간다. 기록과 실제 Git·코드가 다르면 실제 상태를 확인해 허용 범위 안에서 정정한다.
- `WORK_STATUS.md`는 현재 기준점, 주요 완료 기능, 남은 작업, 중요한 미검증 항목만 간결히 기록한다. 가능한 한 실제 코드 변경과 함께 갱신한다.
- 일반 소규모 수정마다 상태 문서만을 위한 별도 브랜치·PR·배포를 만들지 않는다. 이미 main에 반영된 작업의 문구 정정 때문에 배포 절차를 반복하지 않는다.

## 7. 공유 자료와 애니메이션

- 실행 결과 팝업의 소리·보드 동작·애니메이션·악보/코드 강조·시뮬레이션은 별도 지시가 없으면 팝업이 열린 동안 전체 실행 단위를 계속 반복한다. 학생 화면에 반복 관련 기술 버튼·문구를 추가하지 않는다. 1회 실행은 별도 지정된 경우만 사용하며, 닫기·바깥 클릭·액션/페이지 이동 시 소리·예약·타이머·강조·버튼 상태를 즉시 정리한다.

- 웹 개발판은 인터랙션과 단계별 동작을 포함한 원본으로 관리한다. 외부 공유판은 교사가 복제·사용하기 쉬운 형태를 고려하고, 개발 소스에 불필요하게 종속시키지 않는다.
- 애니메이션은 학습 이해에 필요한 경우 기존 슬라이드 기능과 간단한 표현을 우선 활용한다. 최종 배포용 GIF 제작·확정이나 공유판의 주요 표현 방식 변경은 범위·용도·대안을 먼저 설명하고 사용자 승인을 받는다.
- 공통화·파일 분리는 현재 요청에 실질적으로 필요할 때만 한다. 파일 수나 향후 재사용 가능성만을 이유로 구조를 확장하지 않는다.
